# ملف الحقيقة لتنفيذ المنصة القانونية - Revision 2

هذا الملف هو المرجع التنفيذي الوحيد للتسلسل المرحلي.

## قواعد عامة

- كل مرحلة يجب أن تكون مكتملة بذاتها.
- كل مرحلة يجب أن تكون قابلة للنشر في بيئة إنتاج حقيقية.
- لا نبدأ المرحلة التالية إلا بعد تحقق شروط الإغلاق الحالية بالكامل.
- بيئة التطوير المعتمدة حصرياً هي: Windows 11، PowerShell، و Visual Studio Code. جميع السكربتات والأوامر يجب أن تدعم هذه البيئة.
- أي ميزة تُبنى داخل مرحلة يجب أن تشمل: قاعدة بيانات، API، صلاحيات، اختبارات، سجلات، مراقبة، وتوثيق، بحسب ما ينطبق عليها.
- tenant isolation تُفرض من الخادم، لا من الواجهة.
- authorization في الـ backend هي المرجع النهائي.
- AI طبقة اختيارية، ولا تتحول إلى سجل قانوني رسمي إلا بعد موافقة بشرية صريحة.
- أي تكامل خارجي يمر عبر adapter/interface فقط.
- لا نستخدم public URLs للمستندات القانونية.
- كل تغيير schema في الإنتاج يحتاج migration.
- كل ميزة حرجة تجارياً تحتاج اختباراً آلياً.
- كل مسار يلامس tenant أو security أو money أو legal record يحتاج audit.
- الواجهة تدعم الإنجليزية والعربية، مع RTL/LTR كامل، i18n، accessibility، responsive layout.

## قرارات يجب تثبيتها في Phase 0

هذه القرارات يجب أن تكون صريحة قبل التنفيذ:

- `Case` هو السجل القانوني canonical.
- يمكن استخدام `Matter` كاسم عرض فقط إذا لزم، لكن schema وdomain terms تبقى `Case`.
- الهيكل التنظيمي المعتمد:
  - `Tenant` = حدود العزل والأمان والفوترة الأساسية.
  - `Organization` = حدود التشغيل داخل tenant.
  - `Branch` = حدود الموقع/المكتب.
  - `Department` = حدود الفريق التشغيلي.
  - `Team` = كيان assignment مرن تحت policies محددة.
- tenant context يُشتق من authenticated membership فقط.
- database-level tenant enforcement يجب أن يكون جزءاً من التصميم حيثما كان مناسباً.
- authorization model = RBAC + ABAC + resource-level authorization + explicit denials.
- integration contracts وidempotency وqueue standards وtransactional outbox يجب أن تُعرّف مبكراً.
- backup baseline يجب أن يبدأ من Phase 1.
- audit foundation يجب أن يبدأ من Phase 2/3.
- conflict check foundation يجب أن يبدأ قبل acceptance لأي matter/case.
- money representation = fixed precision decimal أو integer minor units فقط.
- workflow definitions وdeadline rules يجب أن تكون versioned.
- AI memory لا تساوي legal record ولا knowledge base ولا case data.
- data classification وdata residency وprovider capability model يجب أن تكون محددة مبكراً.

## تعريف "مكتمل"

المرحلة تعتبر مكتملة فقط إذا تحقق الآتي:

- جميع السيناريوهات الأساسية تعمل end-to-end.
- الـ API موثق في OpenAPI أو ما يعادله.
- الـ data model والمهاجرات جاهزة.
- الاختبارات الأساسية ناجحة: unit + integration + e2e أو ما يلزم حسب النطاق.
- السجلات والتنبيهات والتتبع موجودة.
- لا توجد dependency مباشرة على provider في domain.
- لا توجد صلاحيات في الواجهة فقط.
- يوجد rollback أو mitigation plan للطرح.
- التوثيق المخصص للمرحلة محدث.

## المسارات المستمرة عبر كل المراحل

- Database design: PostgreSQL مع foreign keys, unique constraints, check constraints, indexes, and migrations.
- Cache: Redis ليس source of truth.
- Concurrency: transactions, unique constraints, idempotency keys, queue deduplication, optimistic locking where needed.
- API: `/api/v1` ثابت، ولا نكسر contracts بصمت.
- Frontend: no business logic, no hardcoded authorization assumptions, no hardcoded translations.
- Testing: كل مرحلة لها tests مناسبة، ومع المراحل الحرجة أضيف security and e2e coverage.
- Documentation: أي قرار معماري أو تغيير سلوك مهم يُوثق.
- Internationalization: العربية والإنجليزية على الأقل، مع دعم كامل للـ RTL/LTR في كل الشاشات والرسائل والنماذج.
- Accessibility: keyboard navigation, semantic markup, proper labels, error handling.
- Observability: logs, metrics, traces, correlation IDs.
- Security: secure defaults دائماً.
- AI: always optional and permission-aware.
- Release: each phase needs rollback or mitigation plan and staging validation.
