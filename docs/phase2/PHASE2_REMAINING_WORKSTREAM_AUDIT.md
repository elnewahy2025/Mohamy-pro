# Phase 2 Remaining-Workstream Audit

**Status:** Phase 2 remains open. This document records the repository audit after acceptance of the audit/outbox/concurrency reliability workstream. It is not a Phase 2 completion declaration and does not authorize Phase 3.

**Audit basis:** The authoritative [`docs/phase2/PHASE2_IMPLEMENTATION_PLAN.md`](docs/phase2/PHASE2_IMPLEMENTATION_PLAN.md), the approved Phase 2 decision documents, the mandatory [`skills/engineering-governance/SKILL.md`](skills/engineering-governance/SKILL.md), the current repository source, the applied migrations, executed static gates, and bounded Windows runtime evidence.

## Executive conclusion

The repository has a verified identity/session foundation, tenant membership and server-derived tenant switching, tenant-aware legacy boundaries, append-only audit persistence, transactional audit/outbox linkage, restricted PostgreSQL runtime enforcement, real Redis/BullMQ delivery, retry/dead-letter behavior, same-session tenant-switch compare-and-set evidence, and a bounded Windows authorization/MFA result including genuine missing-MFA denial. The invitation and administrative onboarding slice now has qualified Windows runtime evidence for creation, acceptance, replay, identity mismatch, revocation, expiry, audit/outbox processing, and cleanup. Persisted inviter-authority revalidation at acceptance and the broader Phase 2 surfaces remain open.

Phase 2 is **not complete** because the remaining dependency chain required by the authoritative plan is not implemented and runtime-verified across authorization, administrative onboarding, generated API contracts, frontend workflows, abuse and identity-data lifecycle controls, complete integration topology and CI, and the future supported deployment boundary. The backend schema containing roles, permissions, assignments, and denials is not equivalent to a policy engine or complete authorization surface.

## Recommended implementation order

The dependency-safe order began with the backend authorization policy engine and MFA assurance boundary. That bounded policy/RLS/API slice now has real Windows evidence recorded in [`docs/phase2/AUTHORIZATION_MFA_RUNTIME_EVIDENCE.md`](docs/phase2/AUTHORIZATION_MFA_RUNTIME_EVIDENCE.md), including the implemented protected administrative session-revocation operation and genuine missing-MFA denial. The positive provider-MFA success path and the full authorization matrix remain open. Invitation administration and frontend permission-aware behavior must continue to use named policies, real MFA cases, and complete negative evidence. All authorization decisions must use the authenticated session and server-derived membership context; frontend claims cannot establish access.

After the bounded authorization policy enforcement was verified, invitation and administrative onboarding was implemented with hashed single-use tokens, explicit inviter authority, tenant and membership lifecycle checks, audit/outbox linkage, enumeration-safe responses, and a real PostgreSQL/Redis/Keycloak Windows runtime verifier. The verifier now qualifies the covered invitation slice. Before treating that slice as fully accepted, persisted inviter `membership.manage` authority revalidation at acceptance must be reviewed and evidenced. The next dependency-safe Phase 2 action is the shared identity/membership DTO contracts and generated-client re-entry gate; abuse/lifecycle controls and full topology/CI evidence should be integrated across those surfaces rather than bolted on afterward.

Every workstream must receive its own implementation plan and evidence record under `docs/phase2/`, use the real dependency chain, run static and runtime tests, and remain explicitly qualified until its acceptance criteria are evidenced. Phase 3 must not begin during this sequence.

## Unverified and blocked items

The following are not inferred as complete merely because schema or adjacent authentication code exists: full RBAC/ABAC/resource policy coverage, branch/department assignment enforcement, explicit denial evaluation, positive Platform Admin provider-MFA success, complete Tenant Admin restrictions, persisted inviter `membership.manage` authority revalidation at invitation acceptance, complete invitation abuse evidence, generated identity/membership client contracts, frontend auth and tenant switching, endpoint-specific abuse limits, profile export/deletion/anonymization, residency enforcement, full browser integration, hosted CI artifacts, and the supported Linux deployment boundary.

No workaround is being used to convert these items into PASS. The Windows audit/outbox/concurrency result is retained as a qualified workstream acceptance only.
