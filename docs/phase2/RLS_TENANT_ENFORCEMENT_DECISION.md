# Phase 2 RLS and Tenant-Enforcement Decision

**Decision status:** Approved by the project owner as part of the standing Phase 2 preflight approval on 2026-08-22.

**Decision date:** 2026-08-22

**Depends on:** [`TENANT_MEMBERSHIP_SWITCHING_DECISION.md`](TENANT_MEMBERSHIP_SWITCHING_DECISION.md), [`API_ENVELOPE_IDEMPOTENCY_DECISION.md`](API_ENVELOPE_IDEMPOTENCY_DECISION.md), and [`ACCOUNT_LIFECYCLE_DECISION.md`](ACCOUNT_LIFECYCLE_DECISION.md)

## Enforcement principle

Application tenant context is necessary but not sufficient. Every tenant-owned database table must use PostgreSQL Row-Level Security (RLS) or an explicitly documented compensating control with equivalent negative tests. The API and worker database roles do not receive `BYPASSRLS`.

A request or job obtains tenant context only after authentication, membership/policy validation, and server-side selection. A browser-provided `tenantId` never establishes database context.

## Table-by-table decision

| Table or table family | Security class | RLS decision | Required compensating control and rationale |
|---|---|---|---|
| `User` | Global identity/PII | No tenant RLS; access is limited to identity/session services and explicit global policies. | Repository methods require authenticated actor or approved operator policy; no ordinary tenant endpoint may query arbitrary users. |
| `ExternalIdentity` | Global identity mapping | No tenant RLS; provider subject mapping is identity-service-only. | Unique `(provider, subject)`; no email-based implicit linking; raw subject is redacted from logs and not exposed in ordinary API responses. |
| `Session` and session-CSRF state | Global user/session state | No tenant RLS; session service uses user/session ownership checks. | Cookie hash lookup, user ownership, revocation state, idle/absolute expiry, and server-side session context are mandatory. |
| `Tenant` | Global security boundary | RLS is not used for the tenant catalog itself. | Tenant reads/writes require named `CanViewTenant`/`CanManageTenant` policies; ordinary APIs receive only membership-authorized tenants; Platform Admin operations require MFA and audit. |
| `Organization`, `Branch`, `Department`, `Team` | Tenant-owned hierarchy | **RLS required.** | Policies compare `tenant_id` to transaction-local `app.tenant_id`; foreign keys and parent-tenant checks prevent hierarchy crossing. |
| `Membership`, role assignments, scope assignments | Tenant-owned authorization state | **RLS required.** | Policies compare tenant context and additionally enforce user/membership ownership through named service policies. Membership-switch transaction uses the pre-switch user identity and target membership validation before setting the new context. |
| Role and permission catalog | Global immutable definitions | No tenant RLS for global catalog rows. | Catalog is read-only to application runtime; tenant role assignments are RLS-protected; mutation requires migration/operator path or explicit Platform Admin policy. |
| Explicit denials | Tenant-owned security state | **RLS required.** | Denials are checked before allow decisions and are append-only/audited; no endpoint may hide a denial by filtering it out. |
| Invitations | Tenant-owned onboarding state | **RLS required.** | Inviter policy, target tenant, expiry, token hash, and single-use state are validated in one transaction. Acceptance uses a controlled pre-context transaction after identity verification. |
| `AuditEvent` | Tenant-scoped or global security events | RLS required for tenant events; global authentication events use a separate global scope and service policy. | Append-only database permissions, actor/tenant scope, redaction, retention ownership, and audit-write path are mandatory. |
| `OutboxMessage` | Tenant-scoped delivery state | **RLS required for tenant events; global events use explicit global scope.** | API mutation transaction sets tenant context; worker receives a validated tenant identifier in job payload, sets transaction-local context, and cannot process a tenant job without it. |
| `IdempotencyKey` | Actor/tenant-scoped replay state | **RLS required for business mutations.** | Scope is server-derived actor + tenant + method + route; replay checks fingerprint and ownership. OIDC protocol exceptions do not use this table. |
| `StorageObject` | Tenant-owned document metadata | **RLS required after Phase 2 tenant key migration.** | Object key prefix contains tenant ID generated by the server; repository authorization and object-storage policy both enforce tenant scope; delete/retention/legal-hold controls remain mandatory. |
| `Health` and operational metrics state | Global operational state | No tenant RLS. | Access is restricted to health/observability policies; no tenant data may be stored in health labels or unbounded metric labels. |

The table decision is revisited when legal-domain tables are introduced. A new tenant-owned table cannot be merged without a row in this matrix, a migration policy, an RLS or compensating-control implementation, and tenant-negative tests.

## Transaction-local context

The API will set context only inside a transaction using PostgreSQL transaction-local settings, conceptually:

```sql
SELECT set_config('app.tenant_id', $1, true);
SELECT set_config('app.user_id', $2, true);
SELECT set_config('app.membership_id', $3, true);
SELECT set_config('app.operation_id', $4, true);
```

The final implementation must use parameterized queries and `SET LOCAL` semantics; it must never concatenate identifiers into SQL. The third argument must be transaction-local so context is cleared automatically at commit or rollback. The RLS policy must fail closed when the setting is absent, empty, malformed, or inconsistent with the membership.

The application must not use a session-level `SET`, a process-global tenant variable, an async-local value as the only database control, or a connection pool default. Every tenant-scoped repository call must execute inside a transaction that establishes the context before the first query. A shared repository helper must make context setup mandatory and reject a missing context before reaching the database.

## Connection-pool and transaction safety

The Prisma/PostgreSQL adapter uses pooled connections. Because context is transaction-local, commit and rollback clear it before the connection can serve another request. The implementation must still prove that:

- A transaction cannot change `app.tenant_id` after authorization without a new policy check.
- A failed transaction rolls back both domain state and context-sensitive writes.
- A connection reused after Tenant A cannot read Tenant A data during a Tenant B transaction.
- A transaction that omits context returns no tenant rows and cannot insert tenant-owned rows.
- Timeouts and aborted transactions do not leave context or locks that affect the next request.
- A Platform Admin operation cannot set a caller-controlled arbitrary tenant without an explicit target policy and audit event.

## Worker and asynchronous boundaries

Every tenant-scoped outbox job contains a validated tenant ID, aggregate ID, correlation ID, trace metadata, and event version. The worker does not infer tenant context from a raw aggregate lookup or from a process-global value. Before handling a job, it validates the event schema and allowed tenant scope, opens a transaction, sets transaction-local context, and processes the job through an idempotent handler.

A missing, malformed, suspended, archived, or unauthorized tenant context causes the job to fail closed and follow the existing retry/dead-letter policy. A worker may process global operational jobs only when the job type is explicitly registered as global and the handler is not allowed to query tenant-owned tables.

Cache keys, search queries, object-storage keys, exports, and integration payloads must include the server-derived tenant scope. A tenant-scoped cache hit with a mismatched context is a security failure and must be treated as a miss/error, never as a valid result.

## Platform Admin and global operations

The application runtime roles do not bypass RLS. Platform Admin is an application authorization role, not a PostgreSQL superuser. A cross-tenant Platform Admin operation must:

1. Authenticate a recent MFA session.
2. Resolve the target Tenant through a named global policy.
3. Open a transaction with the target tenant context.
4. Execute the narrow operation through the same RLS-protected repository path used for tenant operations.
5. Emit an append-only audit event containing actor, target tenant, policy, reason, and result.

Global catalog operations that genuinely do not belong to a Tenant use explicit global tables and policies. They cannot be used to read tenant-owned rows through joins without a target-tenant context.

## Required acceptance evidence

| Requirement | Required proof |
|---|---|
| RLS default deny | Direct database reads/inserts against tenant-owned tables without context return no rows or fail; missing/malformed context never widens access. |
| Tenant isolation | Tenant A and Tenant B API tests prove read/list/search/write/export/download/cache/queue isolation. |
| Pool reuse | A real pooled-connection test alternates Tenant A and Tenant B and proves no context or data leakage. |
| Transaction rollback | A failing mutation rolls back domain state, outbox, audit, and idempotency state together. |
| Hierarchy integrity | Cross-tenant parent/child references are rejected by database constraints and RLS. |
| Membership switching | Pre-switch validation can inspect only the authenticated user’s candidate memberships; post-switch context is the target membership; audit is written. |
| Worker context | Real Redis/PostgreSQL worker jobs reject missing/wrong tenant context and process valid jobs only within the correct context. |
| Platform Admin | Cross-tenant operation requires MFA, target policy, tenant context, and audit; runtime roles do not have `BYPASSRLS`. |
| Storage/cache/search | Tenant scope appears in generated object keys, cache keys, search filters, exports, and integration requests; mismatches fail closed. |
| Migration | Fresh and existing Windows migration deployment, schema checks, RLS policy checks, and rollback/mitigation review pass without reset or migration-table edits. |
