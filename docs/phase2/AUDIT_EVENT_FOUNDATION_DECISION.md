# Phase 2 Audit-Event Foundation Decision

**Decision status:** Approved by the project owner as part of the standing Phase 2 preflight approval on 2026-08-22.

**Decision date:** 2026-08-22

**Depends on:** [`AUTHENTICATION_ARCHITECTURE_DECISION.md`](AUTHENTICATION_ARCHITECTURE_DECISION.md), [`ACCOUNT_LIFECYCLE_DECISION.md`](ACCOUNT_LIFECYCLE_DECISION.md), [`TENANT_MEMBERSHIP_SWITCHING_DECISION.md`](TENANT_MEMBERSHIP_SWITCHING_DECISION.md), and [`RLS_TENANT_ENFORCEMENT_DECISION.md`](RLS_TENANT_ENFORCEMENT_DECISION.md)

## Decision

Phase 2 includes a real PostgreSQL append-only audit-event store. Audit persistence is not ordinary application logging and is not deferred entirely to Phase 3. Phase 3 may extend the event vocabulary and downstream retention/analytics, but Phase 2 must make authentication, membership, authorization, denial, tenant-switching, and privileged-access events durable, authorized, redacted, queryable, and retained according to the frozen policy.

The event record is written in the same database transaction as the state change when an operation changes application state. The event and its transactional outbox record commit or roll back with the mutation. Authentication events that do not change a domain record still use a transaction for the audit event and session state. A failed audit write fails closed for the protected operation; the system never reports a privileged operation as successful while silently losing its audit event.

## Event model

The Phase 2 `AuditEvent` model must contain at least:

| Field | Requirement |
|---|---|
| `id` | UUIDv4/non-sequential immutable event ID. |
| `eventType` | Stable namespaced type, such as `auth.login.succeeded`, `membership.suspended`, `authorization.denied`, or `tenant.switch.succeeded`. |
| `eventVersion` | Positive integer for payload evolution. |
| `category` | `AUDIT` or `SECURITY`. |
| `outcome` | `SUCCEEDED`, `DENIED`, `FAILED`, or `REVOKED`. |
| `actorUserId` | Application User ID when known; nullable only for unauthenticated attempts. |
| `actorMembershipId` | Membership used for the operation when applicable. |
| `tenantId` | Server-derived tenant ID when a tenant context exists; nullable only for global/provider-boundary events. |
| `targetType` / `targetId` | Resource type and non-sequential identifier, without legal content. |
| `policy` | Named authorization policy evaluated, such as `CanManageMembership` or `CanSwitchTenant`. |
| `reasonCode` | Controlled, non-secret reason or failure code. |
| `correlationId` | UUIDv4 propagated from the request or generated for an internal operation. |
| `traceId` | OpenTelemetry trace ID when available. |
| `ipHash` / `userAgentHash` | Optional privacy-preserving security telemetry using a versioned keyed hash; raw values are not stored in the event. |
| `metadata` | Versioned, schema-validated, redacted JSON metadata with bounded size. |
| `occurredAt` | UTC timestamp generated by the server/database. |
| `createdAt` | Immutable persistence timestamp. |
| `retentionUntil` | Server-calculated retention boundary, at least seven years for Phase 2 audit/security events unless a stricter legal policy applies. |

The database must enforce non-null fields required for the event category, bounded metadata size, valid enum values, valid timestamps, and tenant-consistent actor/membership/target relationships where applicable.

## Event vocabulary

The initial Phase 2 vocabulary includes:

| Area | Events |
|---|---|
| Authentication | `auth.login.started`, `auth.login.succeeded`, `auth.login.denied`, `auth.logout`, `auth.session.revoked`, `auth.session.refresh_failed`, `auth.mfa.step_up.succeeded`, `auth.mfa.step_up.denied`. |
| User and identity | `identity.created`, `identity.linked`, `identity.disabled`, `identity.suspended`, `identity.deleted`, `identity.provider_reconciled`. |
| Invitation and membership | `membership.invited`, `membership.accepted`, `membership.rejected`, `membership.suspended`, `membership.expired`, `membership.removed`, `membership.reinstated`. |
| Authorization administration | `role.assigned`, `role.removed`, `permission.granted`, `permission.denied`, `denial.created`, `denial.removed`. |
| Tenant operations | `tenant.created`, `tenant.suspended`, `tenant.archived`, `tenant.switch.succeeded`, `tenant.switch.denied`, `tenant.bootstrap.succeeded`, `tenant.bootstrap.denied`. |
| Privileged access | `privileged.operation.succeeded`, `privileged.operation.denied`, `break_glass.requested`, `break_glass.approved`, `break_glass.expired`. |

Every event type has a versioned payload schema, an actor/policy requirement, a tenant/global scope, a redaction rule, and a test. Event names are not derived from arbitrary client input.

## Append-only enforcement

The application runtime database roles may insert audit events through a dedicated service path and may read only through authorized audit query policies. They cannot update or delete persisted events. The schema and migration must enforce:

- No `UPDATE` or `DELETE` privilege for the API/worker runtime role on `AuditEvent`.
- Database triggers or equivalent constraints reject changes to immutable event identity, actor, scope, payload, or timestamps.
- Retention cleanup is a separately authorized, auditable operation and cannot delete records before `retentionUntil` without an approved legal-retention workflow.
- Legal holds prevent deletion or alteration even after ordinary retention expiry.
- Audit queries are paginated, tenant-scoped by RLS or global security policy, rate-limited, and themselves auditable when privileged.
- An audit write cannot be performed on behalf of an arbitrary actor supplied by the browser; actor context comes from the authenticated session or trusted internal operation.

The integrity design records an event payload hash and schema version. A later hardening decision may add a chained integrity hash or external immutable archive, but Phase 2 must already provide database append-only permissions, tamper-resistant constraints, authorized reads, and retention/legal-hold controls.

## Redaction and privacy

Audit events may contain resource identifiers, controlled metadata, policy names, outcomes, and security-safe reason codes. They must never contain passwords, access tokens, refresh tokens, authorization codes, cookies, invitation tokens, MFA secrets, raw provider subjects, full email addresses where not necessary, document contents, client financial details, privileged communications, or unbounded request bodies.

The event writer uses allowlisted metadata schemas per event type. It rejects unknown sensitive fields, truncates bounded text, and redacts values before persistence. Logs and traces carry only the event ID, type, outcome, correlation ID, and safe target metadata; they do not duplicate the full event payload.

## Authorization and RLS

Tenant audit events are protected by the tenant RLS decision. Global authentication events use explicit global scope and can be read only by named Platform Admin/security policies. Tenant Admin may read security/audit events only within the active Tenant and only when the authorization matrix allows it. Ordinary users cannot query raw audit history unless a later product policy explicitly grants a filtered self-history view.

Platform Admin access to audit events requires recent MFA, a named purpose/reason, target scope, and an audit event about the audit query itself. Audit-event reads never permit access to tenant content that the underlying user could not access.

## Outbox and tracing

For state-changing operations, the audit event, domain mutation, idempotency completion, and outbox enqueue share one transaction. The outbox payload includes event type/version, audit event ID, aggregate ID, server-derived tenant ID where applicable, correlation ID, and W3C traceparent metadata. Worker delivery is idempotent and never creates a second audit event for a duplicate delivery.

For authentication events, the API creates the audit record and session state transactionally before returning success. For denied requests, the denial event is persisted before the controlled denial response when the request is authenticated; unauthenticated login attempts use the provider-safe global scope.

## Retention and operations

Audit and security events have a default retention of seven years, matching the frozen observability policy. PostgreSQL is the system of record for Phase 2 audit events. Retention ownership, backup/restore coverage, legal holds, authorized purge, and evidence of effective retention are documented before release. The current Windows-Docker environment may verify schema, write, query, immutability, retention calculation, and legal-hold behavior, but it does not prove production-grade availability or off-machine disaster recovery.

Metrics use bounded event-type and outcome labels only. The following metrics are required without using user IDs, tenant IDs, email addresses, or raw target IDs as labels:

- `mohamy_audit_events_total{event_type,category,outcome}`
- `mohamy_audit_write_failures_total{category}`
- `mohamy_audit_query_denials_total{reason}`
- `mohamy_audit_retention_purge_total{result}`

## Required acceptance evidence

| Requirement | Required proof |
|---|---|
| Durable persistence | Real PostgreSQL writes authentication, membership, denial, switch, and privileged events and returns persisted rows. |
| Append-only enforcement | Runtime `UPDATE`/`DELETE` attempts fail; immutable fields cannot change; authorized retention/legal-hold path is tested. |
| Transactionality | Mutation, audit event, outbox, and idempotency state commit or roll back together. |
| Authorization | Tenant Admin, ordinary user, Platform Admin, and unauthenticated audit-read behaviors match policy. |
| Redaction | Source, database, logs, traces, and API responses contain no tokens, passwords, invitation secrets, or legal content. |
| Scope isolation | Tenant A cannot read Tenant B audit events; global events require explicit policy. |
| Duplicate delivery | Duplicate outbox delivery does not create a second audit event. |
| Retention | Seven-year `retentionUntil`, legal hold, backup/restore, and authorized purge behavior are persisted and verified. |
| Traceability | Event ID, correlation ID, trace ID, outbox ID, actor, tenant, policy, and outcome are linked without sensitive payload leakage. |
